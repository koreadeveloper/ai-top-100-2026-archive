- 환경변수 이름만 있는 .env.example과 비밀키 없는 코드 템플릿을 준비한다. 실제 키는 비밀 저장소에 둔다.
- 모델 앱 구독과 API의 인증·잔액을 각각 확인한다. 런타임 모델 변경은 실제 장애가 있을 때 검토한다.
- 사람 입력/컴퓨터 사용의 질문 한 건 완료 시간을 비교해 자동화 사용 여부를 정한다.
- 지식 원장, 질문 원장, 평가 결과, 동결 체크리스트를 준비한다.

## 시작 15분
규정에서 출력 형식·제한시간·최대 길이·API 한도·허용 자동화·금지 사항·제출 이후 변경 제한을 추출한다. 미확인 조건은 미확인으로 남긴다. 최소 채널 왕복과 인증된 테스트 API 하나를 통과시킨다. 예시 한 건으로 평가 파이프라인을 시작한다.

## 조사와 구현 병행
자료 수집 담당은 현재 사용 가능한 인터뷰 창구와 문서 참조 관계를 관리한다. 분석 담당은 단순 요약보다 시행일·권한·예외·관찰 범위를 추출한다. 개발 담당은 검증 가능한 변화만 적용한다. 평가 담당은 채점 이유와 실제 호출 결과를 함께 확인한다. 역할 분리는 권장 구조이며 여러 AI가 필수는 아니다.
공통 파일: facts.csv / questions.csv / conflicts.md / evaluation.csv / decision-log.md. 담당자 간에는 새 사실과 파일 경로만 넘기고 전체 채팅을 반복 복사하지 않는다. 같은 파일을 동시에 수정하지 않는다.

## 질문을 고르는 기준
예상 가치 = 실제 실패를 줄일 가능성 × 영향도 + 아직 없는 원문·도달 경로의 가치 - 질문·전송·대기 비용. 수식의 가중치는 공식 채점이 아니라 운영 판단용이다.
우선: 실패 TC에 필요한 근거 → 참조 조항에 연결된 자료 → 날짜·로트·코드가 있는 사건 → 표본·판본·권한 충돌 → 남은 경험 지식.
같은 사람이 두 번 연속 같은 거절·미확인을 답하면 상태를 ‘경로 막힘’으로 남기고 소유자·관계도·원문 인덱스를 찾는다. 두 번은 권장 전환 기준이며 새로운 근거가 있으면 재질문할 수 있다.
다른 인물에게 동시에 보낼 수 있지만 같은 인물은 답을 받은 뒤 후속 질문한다. 실제 규정의 글자수·횟수 제한을 따른다.

## 코드에서 보장할 항목
정규화된 TC가 API 헤더에 전달되는지, 실제 조회 출처가 있는 ID인지, 본인 귀속이 검증됐는지, 금액·수량·필수 필드가 맞는지, 타임아웃·429·5xx 재시도가 중복 실행을 만들지 않는지 확인한다. 시스템 전체 권한 검증을 단일 프롬프트에 맡기지 않는다.
도구의 병렬 실행은 서로 의존하지 않는 읽기 작업에 한정해 검토한다. 주문 조회 후 그 결과로 환불하는 단계는 순서가 있다. 사용자가 병렬 작업자를 원해도 한 화면의 입력을 서로 충돌시키지 않는다.

## 마감 전
30분 전: 높은 위험의 기능 추가를 중단하고 공개 예시와 실제 채널을 우선한다.
15~10분 전: 사용자가 정한 시각에 수집·수정을 동결한다. 아직 실패한 API는 성공으로 기록하지 않는다.
제출 전: commit, 배포 버전, health, 실제 카카오 답장, 테스트 API 결과, App ID, 디브리프, 제출 완료 화면을 보관한다. reset은 규정과 사용자 권한 안에서 제출 전만 검토한다.
제출 후: 운영 시스템을 변경하지 않고 오프라인 회고와 자료만 만든다.
